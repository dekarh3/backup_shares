# ТЗ: backup_shares

## Стек
Win7 c файловой системой NTFS, Python 3.8.10, croniter, pystray, интерфейс TCL/TK, SQLite, robocopy, VSS (Volume Shadow Copy Service).

## Цель
Ежедневный инкрементальный и еженедельный полный бэкап файлов на
SMB-шарах с возможностью восстановления состояния файлов на
произвольную дату.

---

## Принципы

### 1. Авторизация
1.1. Мастер-пароль на вход, хранящиеся в отдельном бинарном файле (credentials.bin). Файл содержит соль и хэш мастер-пароля (для верификации). Сами пароли шар шифруются ключом, производным от мастер-пароля.

1.2. Шифрование паролей шар:
- Пароли доступа к SMB-шарам в .ini шифруются симметричным ключом, производным от мастер-пароля (например, через PBKDF2 → AES).
- При смене пароля входа все пароли шар перешифровываются (см. п. 1.3).
- **Атомарная запись:** Запись в `.ini` и `credentials.bin` должна производиться атомарно: сначала запись во временный файл, затем `os.replace()` (или `MoveFileEx` в Win). Это предотвращает потерю конфигурации при сбое питания.

1.3. Если credentials.bin отсутствует — запускается процесс первичной инициализации:
- Инициируется создание мастер-пароля без указания прошлого пароля. 
- Логины/пароли к шарам удаляются (если шары прописаны в .ini) и требуется их заполнить заново.
-  Если в таблице `current_state` нет записей, то добавляем одну, если есть то перезаписываем её : `status` = `idle`, `current_backup_id`, `current_backup_timestamp`, `last_success_backup_id`, `last_success_backup_timestamp`, `last_success_backup_type` = NULL, `last_processed_cron_time` = 3 часа.

1.4. Диалог смены мастер-пароля:
- Пользователь вводит текущий (старый) пароль и новый пароль дважды.
- При успешной проверке старого пароля программа расшифровывает все сохранённые в `.ini` пароли шар старым ключом, шифрует их новым ключом (производным от нового пароля) и перезаписывает `.ini` файл.
- Бинарный файл с хэшем мастер-пароля перезаписывается новым хэшем.
- Если старый пароль неверен — операция отменяется с предупреждением.

### 2. Конфигурация
#### 2.1. Конфиг редактируется из интерфейса, сохраняется в текстовый `.ini` файл. В конфиге:
2.1.1 Для каждой шары:
- share_nic - короткое имя-метка шары
- share_name — UNC-путь (например, \\server\share)
- login / password — зашифрованные учётные данные доступа к шаре (login может быть в формате `DOMAIN\username` или `.\username`)
- mt_threads — количество потоков для robocopy (параметр /MT:n)

2.1.2 Для каждого профиля расписания (cron-профиля):
- cron_id - id (автоинкремент)
- backup_type (ENUM: `full` / `incremental`)
- cron_request - cron-выражение для расписания бэкапов
>В системе может быть настроено несколько cron-профилей (например, один для полных бэкапов по воскресеньям, другой для инкрементальных по будням). Каждый активный cron-профиль применяется ко всем настроенным шарам одновременно.

2.1.3 `target_backup_path` - локальная папка для сохранения бэкапов.

### 3. База данных SQLite
3.1. Таблица `backuped_files` — сохранённые файлы во время проведённых
полных и инкрементальных бэкапов:
- `id` (PK, автоинкремент)
- `backup_id` (FK, id бэкапа)
- `cron_id` (FK, id крона)
- `backup_type` (ENUM: `full` / `incremental`)
- `share_nic` (короткое имя шары) 
- `share_name` (имя/путь шары) 
- `file_path` (относительный путь файла внутри шары) 
- `file_size` (размер в байтах)
- `file_attributes` (атрибуты NTFS в JSON)
- `file_permissions` (ACL / права доступа в JSON)
- `created_time` (дата/время создания файла)
- `modified_time` (дата/время изменения файла)
- `backup_timestamp` (дата/время сохранения в бэкап)
- **Индексы:** Создать индексы по `backup_id`, `share_nic`, `file_path` для ускорения запросов.

3.2. Таблица `deleted_files` — файлы, удалённые из источника между
бэкапами: 
- `id` (PK, автоинкремент)
- `backup_id` (FK, id инкрементального бэкапа, в ходе которого обнаружено удаление)
- `full_backup_id` (FK, id полного бэкапа, на базе которого обнаружено удаление)
- `cron_id` (FK, id крона)
- `share_nic` (короткое имя шары) 
- `share_name` (имя/путь шары) 
- `file_path`
- `deletion_timestamp` (дата/время, когда файл был обнаружен как отсутствующий в источнике)

3.3. Таблица `current_state` — текущее состояние программы (одна строка):
- `status` (ENUM: `idle` / `running` / `error` / `no_space`)
- `current_cron_id` (id крона текущего работающего бэкапа)
- `current_backup_id` (id текущего работающего бэкапа, NULL если простаивает)
- `current_backup_timestamp` (дата/время старта текущего бэкапа)
- `current_backup_type` (тип текущего бэкапа: `full` / `incremental`)
- `last_success_cron_id` (id крона последнего удачного бэкапа)
- `last_success_backup_id` (id последнего удачного бэкапа)
- `last_success_backup_timestamp` (дата/время последнего удачного бэкапа)
- `last_success_backup_type` (тип последнего удачного бэкапа: `full` / `incremental`)
- `last_processed_cron_time` (дата/время, за которое бэкап уже точно отработал - упрощает логику проверки нестартованности)

3.4. Временная таблица `temp_file_list` — список файлов текущего
бэкапа:
- Создаётся как обычная таблица с префиксом `temp_` (не TEMPORARY TABLE, чтобы избежать проблем с соединениями SQLite).
- Поля: `share_nic`, `share_name`, `file_path`, `file_size`, `file_attributes`, `file_permissions`, `created_time`, `modified_time`, `status` (ENUM: `pending` / `copied` / `skipped`).
- **Важно:** Используется одно выделенное соединение SQLite на весь процесс бэкапа, создаваемое при старте бэкапа и закрываемое после его завершения.

3.5. Таблица `backup_log` — журнал всех бэкапов:
- `backup_id` (PK, автоинкремент) — единый сквозной счётчик для всех типов бэкапов. 
- `backup_type` (`full` / `incremental`)
- `cron_id` (ссылка на id cron-выражения из .ini, по которому был запущен бэкап)
- `start_time`
- `end_time`
- `status` (`running` / `success` / `error` / `cancelled` / `no_space` / `skipped`)

3.6. Таблица error_cooldown:
- `cron_id` (PK)
- `last_error_time` (дата/время последней ошибки)
- `error_count` (счетчик последовательных ошибок)

3.7. Таблица current_file_state — актуальное состояние файлов на шарах (снимок на момент последнего бэкапа):
- `share_nic` (короткое имя шары)
- `file_path` (относительный путь)
- `last_backup_id` (id бэкапа, в котором файл был сохранен или подтвержден)
- `file_size`
- `modified_time`
- `attributes_hash` (хэш атрибутов и прав доступа для отслеживания изменений)
- Первичный ключ: (`share_nic`, `file_path`)
- Примечание: Таблица обновляется (UPSERT) при каждом успешном полном и инкрементальном бэкапе. Если файл удаляется, запись удаляется из этой таблицы.

### 4. Интерфейс: переключатель и индикатор
4.1. Переключатель «Запуск просроченных бэкапов» (вкл/выкл).
4.2. Индикатор состояния (`idle` / `running` / `error` / `no_space`),
видимый из любого окна/вкладки интерфейса, включая трей.
4.3. Кнопка «Отменить текущий бэкап» (активна только в статусе `running`). При нажатии процесс robocopy завершается, временные папки переименовываются в `_cancelled` (не удаляются для последующего анализа), в `backup_log` пишется статус `cancelled`.

### 5. Планировщик запуска бэкапов
5.1. Программа может быть свёрнута в трей. Фоновый поток каждую минуту
проверяет текущее время и cron-расписание.

5.2. Бэкап запускается, если **все** следующие условия выполнены:
- Индикатор состояния = `idle` или `error`.
- Для данного cron-выражения (по его `cron_id`) текущее время попадает в окно запуска (совпадение с точностью до минуты).
- **Проверка нестартованности:** `last_processed_cron_time` из `current_state` для данного `cron_id` меньше текущего времени, рассчитанного парсером cron как предыдущее срабатывание этого выражения. Это упрощает логику и делает её устойчивой к переводам времени и сбоям BIOS.

5.3. Поведение переключателя «Запуск просроченных бэкапов»:
- **Выключен:** бэкап запускается только при точном совпадении текущей минуты с cron-расписанием (окно = 1 минута).
- **Включен:** бэкап запускается в любой момент, когда текущее время **превышает** рассчитанное cron-время нестартованного бэкапа.
- **Кулдаун при ошибках (Cooldown):** Если предыдущая попытка запуска этого cron_id завершилась со статусом error или no_space, повторный автоматический запуск возможен не ранее чем через N минут (настраивается в конфиге, по умолчанию 60 минут). Время последней ошибки хранится в таблице error_cooldown. Это предотвращает спам попыток при отвалившейся сети или отсутствии места.
>Бесконечный повтор при ошибке при включенном «Запуск просроченных бэкапов» — задуманное поведение, для остановки нужно выключить и разбираться с ошибкой

5.4. Приоритет
- Если одновременно подошли полный и инкрементальный бэкап — выполняется полный. Инкрементальный бэкап для данного срабатывания cron пропускается (считается, что полный бэкап его покрыл), в `backup_log` для пропущенного инкремента **создается запись со статусом `skipped`**, чтобы не нарушать непрерывность логов.
- Одновременно может выполняться только один бэкап.

### 6. Единственный экземпляр и проверка привилегий при запуске
6.1. При старте программа проверяет, запущена ли она от имени Администратора через win32security или ctypes.
6.2. Если нет — вывести сообщение об Ошибке: *«Для корректного сохранения
прав доступа (ACL) программа должна быть запущена от имени Администратора* с кнопкой «Выход».
6.3. Обработка заблокированных файлов (locked files) реализуется через **VSS (Volume Shadow Copy Service)**:
- Перед началом бэкапа создается теневая копия (shadow copy) каждой SMB-шары.
- Robocopy работает с теневой копией, что позволяет копировать заблокированные файлы.
- После завершения бэкапа теневая копия удаляется.
6.4. Запуск нескольких экземпляров программы заблокирован (через
именованный мьютекс или lock-файл).

### 7. Структура папок
7.1. Для каждого бэкапа создаётся пара папок в целевом хранилище:
- `<backup_id>_<дата бэкапа DDMMYYHH>_main` — **постоянная** папка, хранит последний валидный бэкап.
- `<backup_id>_<дата бэкапа DDMMYYHH>_temp` — **временная** папка, создаётся на время бэкапа.
7.2. Для каждой шары внутри папок бэкапа создаётся папка с коротким именем-id шары `share_nic`

### 8. Процесс полного бэкапа
8.1. Удалить все временные папки (`*_temp`), теневые копии VSS и временные таблицы (`temp_file_list`, `temp_deleted_list`) от ранее прерванных бэкапов.

8.2. Записать в `backup_log` новую запись с `status = running`,
получить `backup_id`.

8.3. **Сканирование через robocopy:** Для каждой шары запустить robocopy с ключами `/L /E /BYTES /NFL /NDL /NJH /NJS /nc /ns /np /XJ /LOG:<log_file>`. Это выведет список всех файлов с их размерами и атрибутами в консоль. Распарсить лог и сохранить данные во временную таблицу `temp_file_list` с `status = pending`. Это значительно быстрее, чем использование `os.scandir` на Python.

8.4. Посчитать суммарный размер **всех** файлов из
`temp_file_list` + **10% запаса** (учитывает кластеризацию NTFS, ADS и рост БД). Проверить свободное место на целевом
диске. Если места недостаточно — останов, статус `no_space` в
индикатор и `current_state`.

8.5. В `current_state`: статус = `running`, `current_backup_id` и
`current_backup_timestamp` = текущие значения.

8.6. Создать временную папку `<backup_id>_<дата бэкапа DDMMYYHH>_temp` для бэкапа и подпапки в ней для каждой шары.

8.7. Создать теневую копию (VSS) для каждой шары.

8.8. Копировать файлы каждой шары в подпапку с помощью robocopy, используя **встроенную многопоточность robocopy** (ключ `/MT:n`, где n — настраиваемое число потоков, по умолчанию 8). Запускать по одному процессу robocopy на шару, не плодить процессы на каждый файл. Ключи robocopy: `/E /XJ /COPY:DATSO /DCOPY:DAT /DCOPY:T /R:1 /W:1 /MT:n /NP /LOG:<log_file>`. Robocopy работает с теневой копией (VSS).

8.9. Парсить лог robocopy после завершения. Для каждого файла обновить `status` в `temp_file_list`: `copied` (если успешно скопирован) или `skipped` (если заблокирован или ошибка).

8.10. Если в процессе работы robocopy возвращает код ошибки, связанный с нехваткой места (Exit Code 8 или 16 с соответствующей записью в логе), бэкап немедленно останавливается, статус меняется на `no_space`, временные папки не удаляются.

8.11. По окончании копирования сверить **локально скопированные файлы** во временных папках (путь + имя, размер, время изменения) с записями во временной таблице `temp_file_list` **только для файлов со статусом `copied`**. Сетевой опрос SMB-шар на этом этапе **не производится**. При сверке `modified_time` допускается временной допуск (delta) не более одной минуты для компенсации рассинхронизации часов между SMB-сервером и локальной машиной.

8.12. Если сверка не прошла — останов, статус `error` в индикатор и `current_state`. Выдать список несовпадений в info-диалоге с кнопкой Ок. Временные папки **не удаляются** для последующего анализа.

8.13. Если сверка прошла успешно:
- Если существует папка `*_trash`, удалить её.
- Переименовать `*_main` → `*_trash` (если существует).
- Переименовать `*_temp` → `*_main`.
- Если шаг 2 или 3 не удался (исключение ОС) — останов, статус `error` в индикатор и `current_state`, не удалять ничего, выдать ошибку в info-диалоге с кнопкой Ок.
- Удалить `*_trash`.
- **Массовая вставка:** Скопировать все записи из `temp_file_list` в `backuped_files` с `backup_type = full` используя `executemany` для производительности.
- Удалить временные таблицы `temp_file_list` и `temp_deleted_list`.
- В `current_state`: статус = `idle`, `current_backup_id` и `current_backup_timestamp` = NULL, `last_success_backup_id`, `last_success_backup_timestamp`, `last_success_backup_type`, `last_processed_cron_time` = текущие значения.
- В `backup_log`: `status = success`, `end_time` = текущее время.

8.14. Удалить теневые копии (VSS).

### 9. Процесс инкрементального бэкапа
9.1. Удалить все временные папки, теневые копии VSS и временные таблицы от ранее прерванных бэкапов.

9.2. Записать в `backup_log` новую запись с `status = running`,
получить новый `backup_id` и `full_backup_id` последнего полного бэкапа.

9.3. **Сканирование через robocopy:** Для каждой шары запустить robocopy с ключами `/L /E /BYTES /NFL /NDL /NJH /NJS /nc /ns /np /XJ /LOG:<log_file>`. Распарсить лог и получить текущий список файлов с атрибутами. Сравнить полученный список с таблицей `current_file_state` (быстрое сравнение по индексу `share_nic` + `file_path` и `attributes_hash`). В результате сравнения сформировать два списка:
- `changed_files` (файлы, которых нет в БД, или у которых изменились `file_size` / `modified_time` / `attributes_hash`). Записать их во временную таблицу `temp_file_list` с `status = pending`.
- `deleted_files_paths` (пути файлов, которые есть в `current_file_state`, но отсутствуют на шаре). Сохранить этот список во временной таблице `temp_deleted_list`.

9.4. Посчитать суммарный размер файлов из `temp_file_list` + **10% запаса**. Проверить свободное место на целевом диске. Если места недостаточно — останов, статус `no_space`.

9.5. В `current_state`: статус = `running`, `current_backup_id` и
`current_backup_timestamp` = текущие значения.

9.6. Создать временную папку `<backup_id>_<дата бэкапа DDMMYYHH>_temp` и подпапки для каждой шары в ней.

9.7. Создать теневую копию (VSS) для каждой шары.

9.8. Копировать только изменённые файлы с помощью robocopy с встроенной многопоточностью и списком файлов, по одному процессу на шару. Ключи: `robocopy <source> <dest> /E /XJ /COPY:DATSO /DCOPY:DAT /DCOPY:T /R:1 /W:1 /MT:n /NP /LOG:<log_file> @<filelist.txt>`. Robocopy работает с теневой копией (VSS).

9.9. Парсить лог robocopy после завершения. Для каждого файла обновить `status` в `temp_file_list`: `copied` или `skipped`.

9.10. Если в процессе работы robocopy возвращает код ошибки, связанный с нехваткой места (Exit Code 8 или 16 с соответствующей записью в логе), бэкап немедленно останавливается, статус меняется на `no_space`, временные папки не удаляются.

9.11. По окончании копирования сверить **локально скопированные файлы** во временных папках с записями в `temp_file_list` **только для файлов со статусом `copied`**. Сетевой опрос не производится. При сверке `modified_time` допускается временной допуск (delta) не более одной минуты для компенсации рассинхронизации часов между SMB-сервером и локальной машиной.

9.12. Если сверка не прошла — останов, статус `error` в индикатор и `current_state`. Выдать список несовпадений в info-диалоге с кнопкой Ок. Временные папки **не удаляются** для последующего анализа.

9.13. Если сверка прошла успешно:
- Если существует папка `*_trash`, удалить её.
- Переименовать `*_main` → `*_trash` (если существует).

### 10. Восстановление на заданную дату
10.1. Диалог восстановления: 
- выбор целевой даты/времени из календаря, ограниченного только датами имеющихся бэкапов
- выбор шары (или «все шары»)
- **обязательный выбор целевой папки восстановления** (восстановление по исходным путям **запрещено** для предотвращения случайной перезаписи системных файлов)
- предупреждение о том, что если в целевой папке есть файлы с такими же именами, они будут перезаписаны

10.2. Алгоритм восстановления:
- Найти последний **полный** бэкап, предшествующий выбранной дате (по
`backup_timestamp` в `backuped_files`).
- Скопировать все файлы этого полного бэкапа в целевую папку восстановления.
- Последовательно наложить все **инкрементальные** бэкапы между найденным полным и выбранной датой (в хронологическом порядке), заменяя файлы более новыми версиями.
- Из таблицы `deleted_files` выбрать записи с `deletion_timestamp` ≤ выбранной даты. Удалить файлы в целевой папке только в том случае, если они отсутствуют в итоговом восстановленном состоянии (то есть не были перезаписаны/созданы заново последующими инкрементами).
- Отобразить пользователю итоговый список восстановленных файлов и журнал операций.
